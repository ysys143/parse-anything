# Processing Tiers and Domain Adaptation — Requirements

> 상태: 필수 목표 계약(보완). `pdf-pipeline-requirements.md`가 정의한 파이프라인 메커니즘을,
> **deterministic ↔ VLM ↔ human 3계층 경계 정책**과 **소스 단위 diagnose-then-configure**(§2.5), 그리고 **도메인 적응 도구** 관점에서 명시한다.
> 관계: 렌더·추출·표·VLM·가드·출력·검증·라이선스의 *메커니즘*은 `pdf-pipeline-requirements.md`가 규정한다.
> 이 문서는 *계층을 어떻게 정하고(P1–P7), 소스마다 진단해 설정하고(§2.5–2.6), 그 설정을 도메인마다 어떻게 적응시키는가(§5)*를 규정한다.
> 핵심 전환: **런타임 per-page 자동 라우팅을 폐기**하고(P7), 소스마다 진단해 프로파일을 정한 뒤 그대로 실행하며, 고정밀이 필요하면 결정론과 VLM을 *둘 다* 돌려 정합한다.

## 1. 원칙 (Principles)

- **P1. 3계층.** 처리는 결정론(T-DET), VLM(T-VLM, = 제품), 검증 오라클(T-HUM, 사람 위치)로 나뉜다. 앞의 둘은 *제품 파이프라인*이고, 셋째는 제품 *바깥*의 검증 위치다. 각 계층은 역할과 *권위(source of truth)*가 다르며, 계층 간 이동은 *에스컬레이션 결정*이다 (위치/권위는 P5–P6, §2).
- **P2. 오류율은 도메인/데이터 종속이다.** 보편 임계값은 존재하지 않는다. 처리깊이·가드·에스컬레이션 정책은 *대상 도메인의 실제 문서에서 측정해 보정*해야 한다 (cf. 파이프라인 §3.5, §8).
- **P3. 사람 검증은 환원 불가능하다.** 자동으로 검증할 수 없는/고위험 잔여는 항상 사람의 몫이다. 목표는 사람 노력을 *제거*가 아니라 *최소화·타겟팅*하는 것이다.
- **P4. 따라서 도구가 제품의 일부다.** 시스템은 *도메인 적응(측정 → 사람검증 → 보정)을 쉽게 하는 도구*를 함께 제공해야 한다. 임계값은 코드가 아니라 측정이 정한다.
- **P5. 오라클은 *위치*지, 파이프라인 구성요소가 아니다.** 제품(파이프라인 = 결정론 + VLM)은 *검증 대상*이므로 **자기 출력의 검증자가 될 수 없다.** `vlm.py` 안에 어떤 모델(Gemini flash-lite든 더 강한 모델이든)을 넣어도 그것은 워커지 오라클이 아니다. **검증 오라클은 파이프라인 *바깥*, 사람과 같은 위치에 선다.** 강한 모델(예: Claude Opus 4.8)은 그 사람 위치에 *자동 검증자*로 앉을 수 있으나, 그래도 파이프라인 구성요소가 아니라 검증 계층(T-HUM)의 점유자다.
- **P6. 용어: 두 "오라클"을 구분한다.** **값 오라클(value oracle)** = born-digital 숫자/텍스트의 권위 소스인 *결정론 텍스트 레이어*(T-DET) — 모델이 아닌 결정론 사실. **검증 오라클(verification oracle)** = 제품 출력을 실제 페이지/source에 대조해 판정하는 *사람 위치의 검증자*(T-HUM, 사람 또는 Opus). 둘은 다른 계층이며 섞어 부르지 않는다.
- **P7. 소스 단위로 *진단 → 설정*하며, 런타임 per-page 자동 라우팅은 하지 않는다.** 결정론 구조검출기(pdf-inspector, ODL)는 문서 종류마다 다르게 오탐하므로(F16) 런타임에 페이지마다 경로를 자동 판정하는 것은 오탐(FP) 도박이다. 대신 **소스(§2.5)마다 한 번(또는 주기적으로) 진단해 *프로파일*을 정하고, 실행은 그 프로파일대로 예측가능하게 한다.** 고정밀이 필요하면 라우팅 대신 결정론과 VLM을 *둘 다* 돌려 정합한다(§2.6). 고품질 진단은 검증 오라클 위치(P5)의 에이전트(1-2)가 수행한다.

## 2. 계층 모델과 권위 (Tier Model & Authority)

| 계층 | 위치 | 권위를 갖는 대상 | 갖지 않는 것 |
| --- | --- | --- | --- |
| **T-DET** 결정론 | 파이프라인(제품) | born-digital의 값·텍스트·bbox·표영역의 source of truth (= 값 오라클) | 스캔, 의미 설명, 결정론이 놓친 복잡 구조 |
| **T-VLM** (제품/워커) | 파이프라인(제품) | 구조/레이아웃 재구성, 스캔(텍스트 레이어 없음), 의미 설명(그림/차트), 결정론이 놓친 복잡 표 구조 | **값의 권위 아님** (숫자는 source 매칭 시에만 신뢰) **+ 자기 출력의 검증 권위 아님** (제품은 자신을 검증 못함, P5) |
| **T-HUM** 검증 오라클 | 파이프라인 *바깥* (사람 위치) | 제품 출력의 최종 검증·판정 권위; flag된/자동 검증 불가 잔여의 권위 | — |

- **R-T1.** born-digital 문서에서 값(숫자/텍스트)의 권위는 T-DET(값 오라클)이다. T-VLM이 낸 값은 결정론 source text와 매칭될 때만 신뢰한다 (cf. 파이프라인 §6).
- **R-T2.** 구조(셀 배치, 병합, 헤더 계층, continuation)의 권위는 결정론이 충분하면 T-DET, 부족하면 T-VLM이다.
- **R-T3.** 자동 검증이 불가능한 잔여(스캔 숫자, 산술 불변식이 없는 표의 구조 오류 등)의 권위는 T-HUM이다.
- **R-T4. (검증 오라클의 점유)** T-HUM = 검증 오라클 위치는 *사람*이 점유하는 것이 기본이며, **강한 모델(예: Claude Opus 4.8)이 그 사람 위치에 자동 검증자로 앉을 수 있다.** 이때 모델은 *제품의 출력(T-VLM 결과)을 실제 페이지 이미지/source에 대조해 판정*한다 — 제품 안에서 또 transcribe하는 것이 아니다. **이 모델은 `vlm.py` provider로 들어가지 않는다** (들어가면 다시 제품/워커가 되어 P5 위반). 자동 오라클은 사람 검증을 *대체*하지 않고 *증폭·선별*한다 (P3): 자동 오라클이 합격시킨 것 중 고위험은 여전히 사람에게 간다.

## 2.5 소스 · 소스 프로파일 · 진단 (Source-level diagnose-then-configure)

자동 라우팅을 폐기(P7)하는 대신, 진단·설정의 단위를 **소스**로 올린다.

- **소스(Source).** 진단·설정의 단위. 개별 페이지·문서보다 상위로, **출처·특성을 공유하는 문서 스트림/부류**다 (예: "한국 정부 HWP 정책문서 피드", "bioRxiv 신경과학 프리프린트", "특정 벤더 견적서").
- **소스 프로파일(Source Profile).** 진단 산출물. 소스당: 실행 모드(§2.6) + 구조 기대(표/그림/복잡구조 위치, 텍스트레이어 건강, 괘선 유무) + 보정 임계 + 위험 핫스팟 + 적용 가드. **소스당 1회, 또는 드리프트 시 주기적으로** 갱신한다. 실행은 이 프로파일대로만 움직인다.
- **진단 도구(Diagnostic) — 두 등급, 같은 산출물(프로파일).**
  - **D-1 내장(서비스).** 자동 VLM 기반. 소스 첫 인제스트·주기 실행. 비용 bounded·확장.
  - **D-2 에이전트 스킬(Claude Code / Codex).** 플래그십 모델을 *코딩 에이전트*로 — 렌더·pypdfium2·ODL·pdf-inspector·VLM을 직접 돌리고 추론·반복한다. 어려운 소스·초기 캘리브레이션용. **검증 오라클 위치(P5)를 점유**하며, §5의 적응 도구(R-A1~A8)를 실제로 수행하는 주체다. 캘리브레이션을 한 번 빡세게 하면(D-2) → 프로파일 확정 → D-1·실행이 그 설정으로 싸게 반복한다.

## 2.6 실행 모드 (두 모드, 프로파일이 지정 — 둘 다 ODL+pypdfium2 병용)

`pypdfium2`와 `ODL`은 *일반 우열*이 아니라 *역할*이 다르다 (F17, 다문서 검증): **pypdfium2 = 값·위치 레이어**(값 *완전성* — ODL은 실데이터 숫자를 누락할 수 있음 + char bbox), **ODL = 구조·청결 텍스트 레이어**(표 격자·읽기순서·헤더/푸터 필터; 단 Java 17 필수). 그래서 두 모드 모두 둘을 함께 쓴다.

- **결정론 모드.** ODL(주력: 표 격자·읽기순서·청결 텍스트) + pypdfium2(숫자 완전성 교차검증·char bbox 백스톱). VLM 0·할루시네이션 0. ODL이 떨군 실숫자(pypdfium2엔 있음)는 플래그.
- **결정론-powered VLM 모드(고정밀).** ODL + pypdfium2 + VLM **셋을 다 입력으로** 정합(reconcile)한다 — pypdfium2=값완전성+bbox앵커, ODL=구조·청결텍스트, VLM=시각 구조. **값 오라클(pypdfium2 숫자)이 VLM 숫자 게이트.** 라우팅이 없으므로 라우팅 누락도 없다.
- **R-M1. Reconciliation precedence.** 소스가 충돌할 때: 값 = pypdfium2 + 값 오라클, 구조 = VLM(또는 ODL이 괘선으로 확신할 때 ODL), 청결 텍스트 = ODL.
- **R-M2.** pdf-inspector·ODL의 구조 판정은 *진단 입력(후보)*이지 권위가 아니다 (F16: 둘 다 문서종속 오탐).

## 3. 계층 경계 (Escalation)

> 재구성(P7): 아래 경계는 더 이상 *런타임 per-page 게이트*가 아니라 **소스 진단의 입력 신호**다 (§2.5). 트리거 집합은 진단이 소스 프로파일의 모드·위험 핫스팟·적용 가드를 정할 때 쓰는 신호이며, 고정밀 모드(결정론+VLM)는 페이지마다 에스컬레이션하는 대신 **둘 다 돌려 정합한다**(§2.6, R-M1).

- **R-B1.** 기본은 *충분한 가장 싼 계층*이다. (진단 시) 트리거가 있는 소스/페이지군에만 상위 계층(VLM/HUM)을 프로파일에 포함한다.
- **R-B2. DET → VLM 트리거:** 파이프라인 §3.4의 집합을 따른다 (스캔/텍스트레이어 부재, 그림·차트 의미설명, 인코딩 깨짐·CID 문제, 산술 불변식 실패, 결정론 table/reading-order/bbox 불완전, 저품질·회전·skew).
- **R-B3. VLM(제품) → T-HUM(검증 오라클) 트리거 (이 문서가 명시):** 아래 신호는 *제품 내부에서* 나오며, 이들이 켜지면 출력은 검증 오라클(사람 또는 Opus, R-T4)이 판정한다. 신호 자체가 검증이 아니다.
  - 가드(source-gate 거부, arithmetic invariant 실패) 통과 못 한 셀
  - 제품 내부 교차검사(이중 provider pass) 불일치 또는 단일 provider 기권 — *제품 내부 신호일 뿐, 판정은 오라클이 한다*
  - 저신뢰 신호(입력 품질 게이트 실패, 저해상도)
  - **산술 불변식이 *없는* 표의 구조 정확성** — universal oracle이 없으므로 도메인 정책상 고위험이면 사람에게
  - 도메인 정책상 고위험 필드(금액, 법적 조항, 식별자 등)
- **R-B4.** 경계는 단일 fuzzy score가 아니라 *결정론 트리거 집합*으로 정한다 (파이프라인 §3.4와 일치).
- **R-B5.** 에스컬레이션 *적극성*은 비용/품질/위험 정책 knob이며, 도메인마다 측정으로 보정한다 (§5).
- **R-B6. 한계의 명시.** 임의의 표/문서 정확성을 자동 보장하는 universal 검증기는 존재하지 않는다. 시스템은 이를 계약으로 인정하고, 잔여를 T-HUM으로 보낸다.

## 4. 계층별 값 무결성 (요약; 상세는 파이프라인 §6)

- **R-V1.** born-digital 값 = T-DET oracle 주입. VLM은 숫자를 새로 읽지 않는다 → 날조 구조적 차단.
- **R-V2.** Source gate(모든 출력 값은 source에 존재) + arithmetic invariant. **arithmetic은 좁은 신호다** — 소계/VAT/수량×단가 같은 계산관계가 있는 표(재무·견적)에만 적용된다.
- **R-V3.** arithmetic이 없는 표(비교표·스펙표·범주표): 값은 source-gate로 안전하지만 *구조*에는 universal oracle이 없다 → T-DET 신뢰 + 결정론 자체 신호(빈 셀/래그드 행/열수 불일치) + 필요 시 T-VLM/T-HUM.
- **R-V4.** 스캔: *값 오라클* 없음(텍스트 레이어 부재) → 프롬프트 기권 + 제품 내부 교차검사 + 입력 품질 게이팅으로 위험을 *표시*하고, 판정은 검증 오라클(T-HUM)이 한다. 잔여 위험 셀은 사람.

## 5. 도메인 적응 도구 (핵심 요구)

오류율이 데이터 종속(P2)이고 사람 검증이 필수(P3)이므로, 시스템은 다음 도구를 제공해야 한다. **이 도구들이 곧 §2.5의 진단이다** — D-2 에이전트(플래그십 코딩 에이전트)가 새 소스를 빡세게 측정·검증·보정하고, 그 산출(R-A4 판정 → R-A5 골든 → R-A7 보정)이 **소스 프로파일**이 되며, D-1 내장 진단·실행이 그 프로파일로 싸게 반복한다.

- **R-A1. (측정)** 도구는 *대상 도메인의 실제 문서*로 파이프라인을 돌려 계층별 산출과 가드 플래그를 생성한다. 보편치가 아니라 *그 도메인의* 오류 특성을 측정한다.
- **R-A2. (리뷰 뷰 = 오라클의 자리)** 원본(렌더된 페이지 또는 표 crop)과 추출물(표·값)을 나란히 제시한다. **이 뷰가 검증 오라클(R-T4: 사람 또는 Opus)이 앉는 자리다** — 제품 출력 vs 실제 페이지를 대조하는 인터페이스이지, 또 다른 제품 경로가 아니다. 자동 오라클(Opus)은 사람과 *같은* 입력(원본+추출물)을 받아 판정을 낸다.
- **R-A3. (위험 surfacing)** 사람은 전수가 아니라 *플래그된 항목만* 검토한다: source-gate 거부, arithmetic 실패, 이중패스 불일치, 저신뢰, 미검증 구조.
- **R-A4. (판정 캡처)** 사람의 맞음 / 틀림 / 값 교정을 기록한다.
- **R-A5. (골든 부산물)** 판정이 누적되어 *도메인 골든셋*이 된다 — 별도 라벨링 작업이 아니라 리뷰의 부산물로. 파이프라인 §8 코퍼스/스코어카드의 입력이 된다.
- **R-A6. (재실행 비교)** 임계값·프롬프트·경로·provider를 바꿔 재실행하고 오류율·비용·사람검토량을 나란히 비교한다.
- **R-A7. (보정)** 처리깊이·에스컬레이션·가드 정책의 knob은 코드 하드코딩이 아니라 이 측정 결과로 설정·재설정한다 (cf. 파이프라인 §3.5).
- **R-A8. (지표)** 도구는 도메인별로 파이프라인 §8 지표(numeric accuracy, hallucination rate, source-gate false-reject rate, routing/처리깊이 정확도, 비용·지연, guard flag precision/recall, 사람검토량)를 산출한다.
- **R-A9. (프라이버시)** 도구는 민감 문서를 provider I/O 제약(파이프라인 §9)에 따라 처리한다. 민감 문서를 공개 호스팅이 필요한 provider 경로로 보내지 않는다.

## 6. 비목표 / 제약 (Non-Goals)

- **N1.** 보편 오류율을 주장하지 않는다 — 오류율은 도메인 종속이다.
- **N2.** 완전 자동 숫자/구조 정확성을 약속하지 않는다. 잔여는 항상 사람 검토 대상이다.
- **N3.** 사람 검증을 제거하지 않는다. 도구의 목표는 사람 노력의 최소화·타겟팅이다.
- **N4.** 임계값을 도메인 측정 전에 하드코딩하지 않는다.
